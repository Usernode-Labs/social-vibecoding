# GitHub independence: how P0–P4 are built, as one change

Written 2026-10-26 by the production session, against canonical main
`b0b1ff542eb6`. The design is `github-independence.md`; the state, promises
and rules are `github-independence-handoff.md`. This file says how the
first five phases are built and shipped **together**, as Evan asked
(2026-10-26), and what is outside the one platform change.

## 1. What ships, and in what order

| Step | Where | Who runs it |
| --- | --- | --- |
| 1. Forgejo (pinned release, CNPG database, retained volume, nightly repository bundles, ingress) | `Usernode-Labs/infra` branch `feat/git-host`; runbook `docs/25-homeroom-git-host.md` there | Evan merges; Argo deploys |
| 2. First start: the `homeroom` service account, the `apps` org, its token into `platform.secrets.sops.yaml` | the runbook's three commands | Evan |
| 3. Recovery: every app's main rebuilt from its rescued image and pushed to `apps/<repo>`; the 7 GitHub-readable repos mirrored | `scripts/github-recovery/` in this change, run from the Mac against `~/homeroom-rescue-2026-10-26` | Evan, with the git host's service token |
| 4. This change (P0–P4) | one PR on `Usernode-Labs/social-vibecoding`, then its 0.1.* chart release | Evan merges; Argo deploys. Its migration makes the new tables and copies the twin rows into `requests` |
| 5. Request import and moves: the rescued board text (393 open requests) and `git-host-moves.sql` | SQL generated by the recovery tool | Evan, on the primary |
| 6. Point the platform at the git host: `config.gitHost`, `networkPolicy.gitHost` in `values/platform.yaml` | a second `Usernode-Labs/infra` PR | Evan merges; the sync's migration Job applies step 5's moves, then the pods start with `GIT_HOST_*` |

An app is repointed only when it has a row in `git_host_moves`, written by
the recovery tool once its repository is on the git host, so a repository
that is not there yet cannot be pointed at. Until step 6, apps keep their
GitHub addresses, and code changes on them are refused as paused. Requests
are rows from step 4 on, whatever the step.

No interim token swap: Evan chose to leave the platform as it is until this
lands (2026-10-26).

## 2. The shape: `github.js` becomes a facade

About 150 call sites reach GitHub through some 30 functions in
`src/services/github.js` (issue, pull request and git-data helpers), and
the test suite stubs those same functions. Rewriting every caller would be
weeks of churn for no behavioural gain. Instead each of those functions now
dispatches on the repository:

- **On the git host** (`services/git-host.js`, owner = `GIT_HOST_ORG`):
  native. Requests are rows (`services/requests.js`), proposals are
  `native_pulls` rows beside their `chat_sessions` (`services/native-pulls.js`),
  refs and merges are git (`services/hosted-git.js`,
  `services/native-merge.js`, `services/repo-mirror.js`).
- **On GitHub** (only `Usernode-Labs/social-vibecoding`, the platform's own
  repository, until P7): unchanged GitHub calls, refused while paused
  (`services/github-pause.js`). Homeroom's own code changes therefore stay
  paused in Homeroom; people change the platform by pull request on GitHub,
  as now.

Requests are native for **every** app, the platform's included: Homeroom is
the only place to request (decision 5), so no request is ever written to a
GitHub issue again.

The functions keep their GitHub-shaped results (`{ number, title, body,
labels, user, createdAt, htmlUrl, state }`, `{ number, merged, head: { sha },
mergeable_state, html_url }`), with `htmlUrl`/`html_url` now Homeroom's own
page for the request or proposal, so existing links keep working and point
somewhere real. P6 renames and removes what is left of GitHub.

## 3. Repository identity

- `apps.repo_url` is the repository's page on the git host:
  `https://<GIT_HOST_URL>/apps/<repo>`. The repository keeps the name it had
  on GitHub, so `owner/repo` keys stored elsewhere need only their owner
  rewritten (`issue_screenshots`, `issue_videos`, `feedback_reports`,
  `title_heal_queue`, `check_runs`, … see §6).
- One parser, `services/repo-ref.js`, replaces `parseGithubUrl` and the ~80
  hand-written `github\.com` regexes: `parse(url) → { host, owner, repo }`,
  `webUrl`, `cloneUrl`, `commitUrl`, `isPlatformRepo`. Both hosts parse;
  `src/workflow/rules/github-url.ts` accepts the git host too.
- `apps.github_repo_url` keeps the old address, for the archive if GitHub
  ever sends it and for the "GitHub main was <sha>" record.

## 4. Native requests (P3)

- `requests (app_id, number, title, body, state, state_reason, labels,
  author_login, created_by, created_at, updated_at, closed_at, closed_by,
  source, recovered_partial)`, unique `(app_id, number)`.
- `request_comments (app_id, number, author_login, user_id, body,
  created_at)` for what used to be GitHub comments (bot posts, close
  notes, spec posts). The Homeroom discussion stays in `chat_messages`
  thread `issue`, as today.
- **Numbering:** `app_numbers (app_id, next_number)`, one per-app sequence
  for requests and proposals, started above the highest number Homeroom
  knows for the app (requests, twin rows, proposals, the rescued boards), so
  `#N` stays unambiguous and every existing key (~25 tables) stays valid.
- **Backfill:** the migration copies the `issues` twin rows (1,921, the
  original filed text, with their open/closed status); the import (step 3)
  overwrites open requests with their current GitHub text. A request known
  only from a twin is marked `recovered_partial`.
- The in-memory list cache, ETags, the stale fallback, overlays and
  suppressions in `github.js` go: a board is a query.
- `Closes #N` stays as it is today in behaviour: `linked_issues` decides,
  the merge closes them, now as a row update instead of a GitHub call.

## 5. Native proposals and merges (P4)

- `native_pulls (app_id, number, title, body, head_branch, base_branch,
  draft, state, merged, merged_at, merge_commit_sha, merged_head_sha, …)`. A proposal's number
  comes from the app's sequence (`app_numbers`), the same one requests use,
  so `#N` names exactly one thing in an app. `chat_sessions.pr_number` keeps
  pointing at it, so nothing keyed on `pr_number` changes.
- `github.createPR`, `getPR`, `updatePR`, `closePR`, `reopenPR`,
  `markReadyForReview`, `listOpenPRs`, `findOpenPRForBranch` and
  `getPRCommits` answer from `native_pulls` for a hosted repository. `getPR`
  reads the head and base from git each time, and `mergeable_state` is
  computed: `dirty` when `git merge-tree` conflicts, `clean` otherwise,
  `draft` for a draft.
- **The merge** (`votes.attemptMerge` → `native-merge.squashMerge`):
  1. fetch the mirror fresh;
  2. refuse when the head is no longer the sha the vote pinned (409, as
     GitHub's pinned merge did);
  3. `git merge-tree` the head onto main (a conflict answers 405 "merge
     conflict");
  4. `commit-tree` one squash commit, `<title> (#N)` and the body;
  5. move main with a compare-and-swap push (`--force-with-lease`). A main
     that moved meanwhile answers "Base branch was modified", and the
     existing retry handles it.
- A revert is the same: `merge-tree --merge-base <sha> main <sha>^` onto a
  new branch, opened as a proposal.
- A repository still on GitHub (only the platform's own): the merge is
  refused as paused while `github-pause` is on, exactly as today's dead
  token would fail it, but with a reason people can read.

## 6. Source paths (P2)

Every path that reads or writes app source follows the repository's host:

- **Create, remix, starters:** `github.createRepo` / `pushFiles` make the
  repository under `apps` with a first commit, as `auto_init` did.
  `app-forker.js` pushes the remix with the service account.
- **Builds:** kpack's source URL and BuildKit's `REPO_URL` are
  `repoRef.cloneUrl`, the internal address. BuildKit's namespace has an
  egress rule for it (infra, step 1).
- **Workers and the push proxy:** workers clone anonymously.
  `worker.execPushFromWorker` pushes with the service account's token,
  passed by credential helper from the environment and never in argv or a
  URL. A GitHub repository is refused permanently as `github_paused`.
- **The mirrors** (`repo-mirror.js`): hosted repositories are mirrored
  whole (not blobless), with the service account. `main-drift-poller`,
  `staging-recovery`, compare, diffs and the proposal handoff read them.
- **Previews, staging, checks and shots:** they fetch by sha
  (`uploadpack.allowAnySHA1InWant` on Forgejo) and skip `refs/pull/*`,
  which hosted repositories do not have.
- **External agents:** `external-agent-head.js`, on the platform, pushes a
  contributor's branch into a hosted repository as the service account. As
  for GitHub, the token is in a throwaway directory's remote URL and is
  redacted from every error.

## 7. What still talks to GitHub after this change

- The platform's own repository and its release chain (P7).
- GitHub account linking and the waitlist's GitHub sign-in: people's own
  identities.
- Importing a public repository by URL (an anonymous clone).
- The recovery tool's mirror of the seven repositories GitHub still serves.

All of it is behind `github-pause`; none of it uses `usernode-bot`.

## 8. Testing

- `npm run test:changed` for each part; the full `npm test` before the PR,
  with the Postgres suites against a local `postgres:17-alpine` (Evan's OK,
  2026-10-26), because platform PRs on GitHub run only the schema check and
  image scans.
- The git paths run against bare repositories over `file://`, with the
  Forgejo API stubbed. `tests/git-host-forgejo.test.js` checks them against
  a real Forgejo 15.0.10. It passed locally on 2026-10-26, with a token
  holding only the scopes the runbook gives (`write:repository`,
  `write:organization`, `read:user`), and found that a branch deleted
  through the API right after a push survived. `deleteRef` pushes the
  deletion now.
