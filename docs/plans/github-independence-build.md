Written 2026-10-26 by the production session, against canonical main
`b0b1ff542eb6`. The design is `github-independence.md`; the state, promises
and rules are `github-independence-handoff.md`. This file says how the
first five phases are built and shipped **together**, as Evan asked
(2026-10-26), and what is outside the one platform change.

Step 4 refuses to repoint an app whose repository is not on the git host
yet (the migration only moves apps listed in `git_host_moves`, written by
the recovery tool), so the order cannot be got wrong silently.

No interim token swap: Evan chose to leave the platform as it is until this
lands (2026-10-26).

## 2. The shape: `github.js` becomes a facade

About 150 call sites reach GitHub through some 30 functions in
`src/services/github.js` (issue, pull request and git-data helpers), and
the test suite stubs those same functions. Rewriting every caller would be
weeks of churn for no behavioural gain. Instead each of those functions now
dispatches on the repository:

- **On the git host** (`services/git-host.js`, owner = `GIT_HOST_ORG`):
  native. Requests are rows (`services/requests.js`), proposals are
  `chat_sessions` rows (`services/native-proposals.js`), refs and merges
  are git (`services/native-merge.js`, `services/repo-mirror.js`).
- **On GitHub** (only `Usernode-Labs/social-vibecoding`, the platform's own
  repository, until P7): unchanged GitHub calls, refused while paused
  (`services/github-pause.js`). Homeroom's own code changes therefore stay
  paused in Homeroom; people change the platform by pull request on GitHub,
  as now.

Requests are native for **every** app, the platform's included: Homeroom is
the only place to request (decision 5), so no request is ever written to a
GitHub issue again.

The functions keep their GitHub-shaped results (`{ number, title, body,
labels, user, createdAt, htmlUrl, state }`, `{ number, merged, head: { sha },
mergeable_state, html_url }`), with `htmlUrl`/`html_url` now Homeroom's own
page for the request or proposal, so existing links keep working and point
somewhere real. P6 renames and removes what is left of GitHub.

## 3. Repository identity

- `apps.repo_url` is the repository's page on the git host:
  `https://<GIT_HOST_URL>/apps/<repo>`. The repository keeps the name it had
  on GitHub, so `owner/repo` keys stored elsewhere need only their owner
  rewritten (`issue_screenshots`, `issue_videos`, `feedback_reports`,
  `title_heal_queue`, `check_runs`, … see §6).
- One parser, `services/repo-ref.js`, replaces `parseGithubUrl` and the ~80
  hand-written `github\.com` regexes: `parse(url) → { host, owner, repo }`,
  `webUrl`, `cloneUrl`, `commitUrl`, `isPlatformRepo`. Both hosts parse;
  `src/workflow/rules/github-url.ts` accepts the git host too.
- `apps.github_repo_url` keeps the old address, for the archive if GitHub
  ever sends it and for the "GitHub main was <sha>" record.

## 4. Native requests (P3)

- `requests (app_id, number, title, body, state, state_reason, labels,
  author_login, created_by, created_at, updated_at, closed_at, closed_by,
  source, recovered_partial)`, unique `(app_id, number)`.
- `request_comments (app_id, number, author_login, user_id, body,
  created_at)` for what used to be GitHub comments (bot posts, close
  notes, spec posts). The Homeroom discussion stays in `chat_messages`
  thread `issue`, as today.
- **Numbering:** `app_numbers (app_id, next_number)`, one per-app sequence
  for requests and proposals, started above the highest number Homeroom
  knows for the app (requests, twin rows, proposals, the rescued boards), so
  `#N` stays unambiguous and every existing key (~25 tables) stays valid.
- **Backfill:** the migration copies the `issues` twin rows (1,921, the
  original filed text, with their open/closed status); the import (step 3)
  overwrites open requests with their current GitHub text. A request known
  only from a twin is marked `recovered_partial`.
- The in-memory list cache, ETags, the stale fallback, overlays and
  suppressions in `github.js` go: a board is a query.
- `Closes #N` stays as it is today in behaviour: `linked_issues` decides,
  the merge closes them, now as a row update instead of a GitHub call.

## 7. What still talks to GitHub after this change

- The platform's own repository and its release chain (P7).
- GitHub account linking and the waitlist's GitHub sign-in: people's own
  identities.
- Importing a public repository by URL (an anonymous clone).
- The recovery tool's mirror of the seven repositories GitHub still serves.

All of it is behind `github-pause`; none of it uses `usernode-bot`.

## 8. Testing

- `npm run test:changed` for each part; the full `npm test` before the PR,
  with the Postgres suites against a local `postgres:17-alpine` (Evan's OK,
  2026-10-26), because platform PRs on GitHub run only the schema check and
  image scans.
- The git paths run against bare repositories over `file://`; the Forgejo
  API is stubbed, and checked once against a real Forgejo before step 2.
